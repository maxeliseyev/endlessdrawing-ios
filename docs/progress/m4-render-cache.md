# M4: стоимость кадра и кеш отрисовки

Статус: в работе. План — однопроходная композиция штрихов, затем поток состояния и параллельная геометрия, затем world-aligned raster tiles по правилам веб-клиента (`../endless-drawing-frontend/src/webgl/tile-plan.ts`, `docs/webgl.md` §4).

## Методика

`Endless DrawingTests/RenderPerformanceTests.swift`, только по флагу `ENDLESS_RENDER_BENCH=1`. Синтетическая детерминированная сцена: 64 точки на штрих, 70% round, по 10% square, chisel и spray, 30% штрихов с opacity 0.5. Штрихи лежат в области 1600×1100 world units вокруг начала координат. Viewport 1210×834 pt ×2 (iPad Pro 11"), zoom 1.

Время кадра — от начала кодирования до завершения GPU (`waitUntilCompleted`, только в тесте), в мс на кадр. Отдельно показаны CPU-кодирование и `gpuEndTime − gpuStartTime`. Pan — среднее по 20 кадрам со сдвигом на 10 pt, zoom — по 10 кадрам ×1.02. `prepare+upload` — однопоточная подготовка геометрии и создание буферов для всей сцены.

Это симулятор iOS 27.0 (iPad Pro 11" M4) на Apple M4 Pro: относительное сравнение «до/после», не показатель устройства. Физический iPad измеряется отдельно, в Instruments → Metal System Trace + Points of Interest (`Signposts`: frame, geometry, snapshot).

## Фаза 2: однопроходная композиция (framebuffer fetch)

На каждый холст или drawable теперь один проход рендеринга. Для каждого штриха:

1. Геометрия поднимает покрытие во втором цветовом вложении (`r8`, blend `max`, то есть объединение, а не сумма).
2. Один треугольник по bbox (+2 px, scissor) читает покрытие через framebuffer fetch и один раз композитит opacity.
3. Отдельный треугольник сбрасывает покрытие.

MSAA-цвет и покрытие — `memoryless`, сводятся в целевую текстуру.

- В симуляторе iOS framebuffer fetch нет («reading from a rendertarget is not supported»). Там и на любом GPU без него остаётся прежний двухпроходный путь. Он же служит эталоном.
- Путь проверяется на реальном Apple GPU стендом `tools/render-harness/run.sh` (macOS, те же исходники рендера). На iPad его проверяет тест `singlePassInkMatchesLegacyTwoPassOutput`.
- Найденная и исправленная ошибка: сброс покрытия в той же функции, что и композиция. Фрагмент выполняется на пиксель и обнулял покрытие сэмплов, которые ещё не скомпозитил. Штрихи получались блёклыми, на стыках треугольников оставались светлые точки.
- Эквивалентность с двухпроходным путём (zoom 0.08 / 1 / 4 и сцена около 1e9): точки, линии и одиночные штрихи совпадают точно. Отличается не больше 0.12% каналов, и только там, где в одном пикселе сходятся края **разных** штрихов: новый путь композитит каждый MSAA-сэмпл над своим фоном, старый — усреднённое покрытие над усреднённым фоном.

## Фаза 3: поток состояния и подготовка геометрии

- `WorldSession` публикует всю сцену подписки в порядке seq, без фильтра по viewport. `update(region:)` больше не публикует: pan и zoom не пересчитывают сцену. Порядок в `SceneStore.ordered` мемоизирован и сбрасывается при любой мутации. Публикации во время приёма снапшота объединяются (не чаще ~60 Гц, последняя всегда доходит).
- Контроллер подготавливает геометрию пакетами по 256 штрихов, параллельно на всех ядрах (`GeometryWorker.prepareBatch`). Первыми идут ближайшие к камере. Renderer обновляется один раз на пакет, а не на каждый штрих.
- Учёт видеопамяти — накапливаемый `GeometryCache.bytes`, без O(N²). Бюджет 64 MiB. Геометрия дальше 512 pt от экрана может вытесняться ради ближней, а дальний штрих ничего не вытесняет и ждёт приближения камеры. «Слишком плотно» показывается только когда не помещается ближняя зона. Лимит в 2000 штрихов снят.

Подготовка геометрии (CPU, симулятор, M4 Pro): последовательно с созданием буферов — 51 / 173 / 320 мс на 250 / 1000 / 2000 штрихов. Пакетно, только CPU-часть — 9 / 38 / 80 мс.
